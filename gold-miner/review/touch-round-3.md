【问题 1（必须 / 调度员直接修）：CPU×4 下降档变慢，T-20 的"中位数 ≥ 40"又不稳定了】
- 现象和证据：
  - 第 3 次触屏测试 **T-20 FAIL**：CPU×4 时整体中位数 **30.1 fps**（要求 ≥ 40），帧时间均值 26.8 ms。
  - 我的探针在产品上跑 CPU×4 6 次，有 **1 次中位数 30.0 fps**（加压时）。其余 5 次是 59.9，但慢帧占比已经是 35–43%，**离 50% 的失败线很近**（加压失败那次是 56%）。
  - 原因是降档时间：
    - 2 → 1.5 在 3.0–5.1 s；
    - 1.5 → 1 在 **7.5–9.7 s**，因为 1.5 → 1 要连续两个窗口的中位数都 > 22 ms。
    - 在 1.5 档时，每个窗口都是 p25 17 ms / 中位数 33 ms、58–79% 的帧是慢帧，第一个窗口就已经明确该降档，却还要多等 2 秒。
    - "严重"条件要求中位数 > 40 ms，但 CPU×4 的典型情况是稳定 30 fps（中位数 33 ms）。这种情况不算"严重"，所以 2 → 1.5 也常常要等两个窗口。
  - 结果是前 7.5–9.7 秒都在低帧率下运行，整局中位数被拉向 30 fps。
- 为什么是问题：
  - 第 2 轮验收标准是"连续 3 次 touch 中 T-20 都通过"，这次没做到。性能断言照样计入判定。
  - 对玩家来说，卡顿的低端机要多卡 2–4 秒才变流畅。
- 修改方向（2 行，改的只是 `G.touchUI` 分支里的数字，CPU×2 的行为不变）：
  - 第 4168 行：
    ```
    const severe = sorted[Math.floor(sorted.length * 0.1)] > 0.022 && med > 0.04;
    ```
    改成
    ```
    const severe = sorted[Math.floor(sorted.length * 0.1)] > 0.022 && med > 0.03;
    ```
  - 第 4171 行：
    ```
    if ((perfBad >= 2 || severe) && G.dprLevel > 1)
    ```
    改成
    ```
    if ((perfBad >= (G.dprLevel >= 2 ? 2 : 1) || severe) && G.dprLevel > 1)
    ```
  - 含义：
    - 90% 的帧 > 22 ms 且中位数 ≥ 30 fps 档（稳定 30 fps）时，立即降档；
    - 在 1.5 档时，一个中位数 > 22 ms 的窗口就足够。中位数本身已经不受零星长帧影响。
    - 2 → 1.5 仍然沿用 p25 加两个窗口，所以 CPU×2 不受影响：CPU×2 时单个窗口最多 45% 慢帧，远低于"严重"要求的 90%。
  - 可选：同步修改 4162 行注释和 T-20 输出文字里的"median > 40 ms"。
  - 我已在 scratchpad 副本上验证过这 2 行：
    - CPU×4 6/6 次降档时间稳定在 **~3.0 s 和 ~5.5 s**，中位数全部 **59.9 fps**，慢帧占比 28–44%；
    - CPU×2 3/3 次保持 2；
    - 打补丁后的副本连跑 2 次 `node tests/run-all.js touch` → **21/21、21/21**。T-20 两次 CPU×4 的中位数都是 59.9，T-13 通过，T-17 通过。
- 验收标准：调度员改完后连跑 3 次 `node tests/run-all.js touch` 都是 21/21（T-20 中 CPU×2 时 `dprLevel === 2` 且 `dprReason === null`，CPU×4 时中位数 ≥ 40），再跑 1 次 `node tests/run-all.js smoke` 5/5。

【问题 2（建议，可调度员直接修 1 行）：650 ms 保护期会吞掉正常玩家的第一次点按】
- 现象和证据（iPhone 13 横屏，真实 tap，从新画面第一次绘制出来开始计时）：

| 场景 | 被吞（无反应） | 生效 |
|---|---|---|
| 主菜单 → 选人：点角色 / "开始" | 339–641 ms | ≥ 640–692 ms |
| 回合结束 → 结算："继续" | 337–637 ms | ≥ 687 ms |
| 结算 → 商店：点卡片 | 341–589 ms | ≥ 638 ms |

| 最后结算 → 终局："再来一局" / "主菜单" | 337–638 ms | ≥ 638–688 ms |
| 暂停菜单："继续" | 不受影响 | 328 ms 起即生效 |

  - 新画面出现后约 **0.64 秒内的点按全部被静默吞掉**，没有任何视觉反馈。
  - 熟练玩家看清画面再点，通常在 400–700 ms，这个区间有一大半会落空。
  - 另外，结算页的"继续"在 `resultsT > 0.4` 时已经画成可用状态，但 0.4–0.65 s 之间点了没反应，看起来像按钮失灵。
  - 一局单人大约要经过 17 个受保护的画面（选人、8 次结算、7 次商店、终局），快手玩家每局会碰到好几次"点了没反应、再点一次"。
- 为什么是问题：不会导致错误操作（再点一次就行），所以不阻塞交付。但这个响应慢的感觉比第 2 轮的 450 ms 明显。真正需要长保护期的只有"查看最终结果 → 再来一局"这一处按钮重叠。
- 修改方向：
  - **方案 A（1 行，调度员可直接修）**：第 541 行
    ```
    G.tapGuardUntil = performance.now() + TAP_GUARD_MS;
    ```
    改成
    ```
    G.tapGuardUntil = performance.now() + (G.screen === 'final' ? TAP_GUARD_MS : 400);
    ```
    我在 scratchpad 副本上用探针验证过：
    - 非终局画面 ≥ 437 ms 的点按全部生效；
    - 终局页 154–617 ms 的连点仍然全部停在 final；
    - "返回主菜单"连点 ≤ 415 ms 停在 start，516 ms 以上会进入选人页。这是"慢速双击"，无害，有"返回"按钮。
    - 这个方案还没跑过测试套件。应用后需跑 1 次 touch 和 1 次 smoke，确认 T-17 仍通过。
  - **方案 B（更好，交给 Builder）**：按位置判断。
    - 每次 pointerdown（包括被吞的那次）都记下 CSS 坐标 `lastDown`。
    - 保护期内只吞**离上一次按下位置 < 48 CSS px** 的点按（这才是双击、连点）；其它位置的点按只受很短的全局保护（~200 ms）。
    - 这样同一位置的连点保护 650 ms 甚至更长都没问题，而去点别处按钮的正常点按 200 ms 后就能生效。
  - 可选：在保护期内把按钮画成 `enabled:false`，让玩家看得出"还不能点"。
- 验收标准：
  - 在非终局的受保护画面（选人、结算、商店、主菜单），新画面出现 450 ms 后去点别处的按钮都能生效；
  - T-17 仍然通过（"查看最终结果"连点 150 / 400 ms 停在 final）；
  - smoke 5/5。

规格层面的问题：
- SPEC-touch §9 仍写着"连续 2 秒**平均**帧时间 > 22 ms 时降一档"。实际实现是：2 → 1.5 用 p25 加两个窗口，1.5 → 1 用中位数，外加"严重"立即降档。这是第 2 轮评估要求改的，规格应同步更新文字，避免下一轮有人按旧规格判定实现偏离。
- 低优先级：iOS 低电量模式会把 rAF 锁在 30 fps。不管是原规格还是现在的实现，都会把 DPR 一路降到 1，画面变糊但帧率不会提高。如果在意，可以在规格里注明"帧时间稳定在 33.3 ms 时不降档"。区分起来有难度，可以留到以后。
