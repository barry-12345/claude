# 性能排查 第 1 轮:"游戏有点卡"

**结论:**
- **最主要的原因在客户端:画布分辨率没有上限。** 电脑版的画布始终按 devicePixelRatio(最高 2)放大。Mac Retina 全屏或大窗口(1728×1117)时,画布达到 3456×1944 ≈ 670 万像素,是 1280×720 窗口的 7.3 倍。每帧都要在这块画布上重画全部内容。
- 原有的"帧慢就自动降分辨率"机制只对触屏开启,电脑上从不触发。
- 联机客户端本身不是瓶颈。每帧"按插值重建 G"、应用增量、GC 加起来不到 1%。
- 但帧变慢会连带让联机多出迟滞感:消息要等一帧画完才处理,测到的到达抖动变大,插值延迟 D 被推到 160–250 ms(正常约 80 ms)。

**测量环境:** 本容器的无头 Chromium,没有 GPU,画布是软件光栅化。没有 WebKit(`/opt/pw-browsers` 下只有 chromium),Safari 没法测。所以绝对数值偏悲观,但各条件之间的相对变化可以参考。测量工具是新加的 `tests/perf-probe.js`。

## 1. 测量(改动前)

条件:联机对战,被测页面 A 用 Mac 典型设置(deviceScaleFactor 2),对手页面 B 是 1280×720、不降速。CPU 降速用 CDP `Emulation.setCPUThrottlingRate`。

| 条件 | 画布 | FPS | p50 / p95 / p99(ms) | >33 ms 长帧 | D |
|---|---|---|---|---|---|
| 联机 1728×1117 DPR2,CPU 4× | 3456×1944 | 8.4 | 117 / 167 / 350 | 100% | 237 ms |
| 本地双人 1728×1117 DPR2,CPU 4× | 3456×1944 | 7.6 | 133 / 150 / 350 | 100% | — |
| 联机 1440×900 DPR2,CPU 4× | 2880×1620 | 9.3 | 100 / 133 / 433 | 100% | 234 ms |
| 联机 1728×1117 DPR1,CPU 4× | 1728×972 | 16.3 | 50 / 83 / 100 | 96% | 163 ms |
| 联机 1280×720 DPR1,CPU 4× | 1280×720 | 21.7 | 50 / 67 / 83 | 57% | 129 ms |
| 联机 1728×1117 DPR2,不降速 | 3456×1944 | 35.2 | 33 / 33 / 50 | 9.8% | 116 ms |
| 本地 1728×1117 DPR2,不降速 | 3456×1944 | 45.0 | 17 / 33 / 33 | 6.6% | — |

主线程时间拆分(CPU Profiler,联机 1728×1117 DPR2,4×):
- JS 只有 0.6 s / 8.7 s 任务时间。
- 93% 是 "(program)",即浏览器原生的画布绘制。
- `netPatch` 0.3%,GC 0.2–0.4%,`netMaterialize` 小到看不出。
- 堆内存约 4 MB,不增长。

把一帧拆开计时(不降速,用 `render()` + `getImageData` 强制同步光栅化):
- 3456×1944 画布:整帧 25.5 ms;去掉物品后 9.7 ms;再去掉矿工和钩子后 6.8 ms。
- 1280×720 画布:整帧 11.5 ms;去掉物品后 3.9 ms。
- 物品的矢量绘制(渐变、路径、文字)是最大的一块,其余部分基本随像素数增长。

另外两个对照:
- 只改 1 个像素的空页面,4× 降速下仍是 60 fps,说明浏览器合成本身不是瓶颈。
- 本地双人和联机的帧时间几乎一样,说明不是联机代码造成的。

非渲染方面(在不卡的情况下):
- 按键后下一帧就显示钩子伸出(O-14:399/399)。
- 插值延迟 D 中位数 88 ms;对手钩子相邻帧跳变 >6° 的只占 0.2%(O-15)。
- 线上实测(调度员):快照间隔 p95 37 ms,jitter 2–5 ms。

## 2. 做了哪些优化(都只影响画面,不改规则、服务端、协议)

**1. 电脑版按帧耗时自动降低画布分辨率**(沿用现有的 `dprLevel` 机制,这次扩展到电脑)
- 对局中每 2 秒看一次帧时间:中位数 > 20 ms 或 90 分位 > 34 ms,就降一档。
  - 第 1 档:分辨率最多是窗口 CSS 尺寸的 1.5 倍。
  - 第 2 档:等于 CSS 尺寸(1 倍)。
- 只降不升。DPR 本来就是 1 的屏幕不参与。
- 快的电脑完全不受影响,画面和以前一样。
- `?perf=0|1|2` 可以强制指定一档(同时关闭自动降档),方便对比测量。

**2. 电脑版绘制上限约 60 fps**
- 游戏逻辑本来就是固定 60 Hz,120 Hz(ProMotion)屏幕上每两次绘制有一次是白做。
- 现在两帧间隔小于 12 ms 时跳过这一次绘制。60 Hz 屏幕不受影响。

**3. `?netdebug=1` 的调试行加了 FPS、最近 1 秒最长帧、当前画质档和画布尺寸**
- 显示效果:`FPS 61 · 最长帧 17ms · 画质档 0 (1280×720) · RTT … · 插值 … · 缓冲 …`。
- `__game.net.stats()` 也多了 `fps`、`maxFrameMs`、`perfLevel` 三个字段。

**试过但没有保留的:"静止物品缓存层"**
- 每 50 ms 重画的版本:FPS 从 8.4 降到 5.7,脚本时间从 0.6 s 涨到 6.5 s。帧本身已经比 50 ms 慢,等于每帧都在重画,又多了一次全尺寸合成。
- 只在物品集合变化时重画、叠加在 1 倍分辨率上的版本:FPS 只从 17.7 提到 18.8,p95 反而变差(从 83 ms 到 100 ms)。
- 两次都没有测出明显收益,按"只做测量证明有效的"原则删掉了。

## 3. 前后对比(同一条件)

| 条件 | 改动前 | 改动后 |
|---|---|---|
| 联机 1728×1117 DPR2 CPU 4×,自动降档,测 16 秒 | 8.4 FPS,p95 167 ms,D 237 ms | 17.6 FPS,p95 117 ms,D 147 ms;画布在开局几秒内降到 1728×972 |
| 同上,稳定在最低档(`?perf=2`) | — | 17.7 FPS,p50 50 ms,p95 83 ms,p99 100 ms |
| 同上,CPU 6×,最低档 | — | 12.2 FPS,p95 100 ms |
| 联机 1440×900 DPR2 CPU 4×,自动 | 9.3 FPS,p95 133 ms | 14.6 FPS(画布 1440×810) |
| 本地双人 1728×1117 DPR2 CPU 4×,自动 | 7.6 FPS,p95 150 ms | 16.5 FPS,p95 133 ms |
| 联机 1728×1117 DPR2 不降速,自动 | 35.2 FPS,>33 ms 长帧 9.8%,D 116 ms | 50.1 FPS,>33 ms 长帧 3.7%,D 89 ms(只降了 1 档,到 2592×1458) |
| 模拟 120 Hz 刷新 | 每秒绘制 108.8 次,主线程忙 14.3% | 每秒绘制 57.3 次,主线程忙 9.6%(游戏速度不变:4 秒走 4.02 秒) |

**目标(DPR2 + 1728×1117 + 4× 降速下 p95 ≤ 20 ms,>33 ms 长帧 ≤ 1%)在本环境达不到。**
- 改动后在这个条件下:p95 83–117 ms,FPS 约 18,FPS 大约翻倍。
- 瓶颈是软件光栅化下每帧重画约 40 个矢量物品和整块画布:1 倍分辨率时,不降速每帧约 11–15 ms,4× 后约 50 ms。
- 再往下压需要重写绘制方式(例如物品预渲染成精灵图并重新设计闪光动画),风险和工作量都超出"低风险优化"。
- 真实 Mac 的 Chrome/Safari 用 GPU 画画布,同样的绘制会快得多。这里的数字只代表"没有 GPU 加速"的最坏情况。

## 5. 用户怎么更新到服务器

**前提:** 本轮提交还没有 push。需要先把分支 `claude/adoring-albattani-ob33dp` 推到 GitHub,服务器上才能拉到。

在服务器上执行(用户的代码在 `~/goldminer-src`,项目目录是 `~/goldminer-src/gold-miner`):

```bash
cd ~/goldminer-src && git pull && cd gold-miner && sudo bash deploy/update-online.sh
```

- `update-online.sh` 会一起换掉 `/var/www/goldminer/index.html` 和联机服务,然后重启服务。页面和服务端的版本号自动对得上。
- 如果正好有人在对局,脚本会拒绝更新并提示。确实要更新就在命令末尾加 `--force`(会结束进行中的对局)。
- 想先看看会做什么,可以把命令里的脚本换成 `sudo bash deploy/update-online.sh --dry-run`。
- 更新后,已经打开游戏的页面会提示"游戏已更新,请刷新页面",两个人都刷新一下即可。

**用户回来后自查:**
- 打开 `https://goldminer.43.161.221.249.sslip.io/?netdebug=1` 联一局,看右下角:FPS、最长帧、画质档。
- FPS 明显低于 60,或画质档降到了 1 或 2,就说明那台电脑绘制吃力。
- 插值延迟明显大于 100 ms,说明有网络抖动,或者帧太慢拖累了消息处理。

## 6. 已知问题
- **测不到真实 Mac。** 没有 WebKit,也没有 GPU,所有数字都来自软件光栅化,不代表 Safari 和 GPU 加速的 Chrome。用户实际卡在哪(绘制、网络、或浏览器扩展等)仍需要用户回来后用 `?netdebug=1` 确认。
- **低端或省电模式下达不到 60 fps。** 自动降到最低档后,4× 降速条件下仍约 18 fps,没有达到目标。进一步优化需要重写物品绘制。
- **自动降档的代价和限制。**
  - 只降不升:一次短暂的卡顿也可能让本局剩下的时间都用较低分辨率(Retina 上略糊),刷新页面恢复。
  - 降档后有一次重算画布和背景,会有一帧较慢。
- **可能的 120 Hz 抖动。** 绘制上限依据"两帧间隔 < 12 ms";极少数屏幕刷新率在 60–80 Hz 之间、且 rAF 间隔抖动时,可能偶尔跳过一帧。
